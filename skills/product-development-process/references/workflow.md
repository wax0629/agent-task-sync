# 阶段与能力门槛

这份通用流程参考了成熟的软件工程训练规范，并将其抽象为不依赖具体组织、工具或日历的执行规则。

## 能力推进

Milestone 不按日历时间划分，而按“已经证明了什么能力”划分。项目可以沿用 MS0-MS4 的名称，但关闭条件必须是能力和证据：

| 能力门 | 最低交付 | 不应提前要求 |
|---|---|---|
| 准备/决策 | 用户、问题、价值、范围、核心假设和 Proposal | 直接编码证明产品成立 |
| 架构主干 | 真实模块、接口、关键模型、可编译调用串联 | 把功能闭合或真实业务结果当作空骨架门槛 |
| 核心路径 | 主要用户故事端到端可演示，架构风险已有验证 | 把完整边界和全部体验打磨当作核心路径前置 |
| 功能闭合 | MVP 范围无占位模块，主要场景可用，有测试和用户反馈 | 无限扩展到非 MVP 功能 |
| 发布交付 | 功能冻结、已知问题、运行/演示环境、版本/tag、Release 和复盘材料 | 发布前继续大规模加功能 |

每次状态报告都写清：当前能力门、已达到的证据、下一项最低必做、可选增强和阻断项。日期可记录，但不能替代验收条件。

## 产品门

产品设计必须回答：为谁做、解决什么、为什么值得做、本期做什么、不做什么、关键备选和取舍、领域概念/信息结构、可验证行为。竞品或替代方案调研服务于取舍，不要求堆砌资料。

有界面产品的顺序是：文字设计 -> 原型 -> 评审 -> 定稿 -> 架构。原型应验证页面层级、关键路径、状态和错误/空状态；不要用一张漂亮截图替代产品决策。

## 架构门

总架构至少要有模块职责、边界、关键数据和真实接口，并能从入口串到核心出口。高风险点要在编码前列出验证方式。架构文档是辅助解释，代码骨架是可持续的主干基线；后续功能应叠加在主干上，而不是每次推翻重来。

## 协作门

工程链路固定为：

```text
Proposal/设计 -> Issue -> 分支实现 -> PR -> 测试 -> Review -> Merge -> 验收记录
```

发现缺口时补新 Issue/变更说明，不编辑历史使过程看起来更完整。每个 Milestone 结束应有目标、全部 Issue、架构演进、验收和交付清单；有发布需求时再创建 Release。
